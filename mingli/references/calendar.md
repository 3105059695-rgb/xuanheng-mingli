# 八字校历与计算

在收集出生资料、公农历日期核验、运行 `scripts/bazi.py`、核对命盘或遇到子时／节气边界时阅读。此脚本计算传统四柱、明确参数后的起运及大运/流年干支表；不自动判格局或计算喜用神分数。

## 输入先校准

先取得明确的历别、年月日和所选时间口径。只核对公农历日期无需出生时刻；用于完整八字时，再取得原始钟表时刻及其来源。需要校核当地时制或太阳时时再取得出生地点；用户已明确指定UTC+8标准时作为计算口径时，可按设定直接计算，不为缺少城市重复停问。保留用户原文；记录换算后的时间另列一项。

- **公历已明确，且采用 UTC+08:00 标准时**：才可将完整出生时刻交给八字脚本 `bazi.py`；纯日期换算按下方日期核验小节。必须传入时间的 `+08:00` 和 `--time-basis utc8-standard`，两者共同表明所选口径。此参数是用户／操作者的确认，不是程序自动识别了出生地历史时制。
- **原始资料是农历**：先确认农历年份、月份、是否闰月与日期，用下方日期核验器检查该月实际存在及日数，再查 [香港天文台公农历对照表](https://www.hko.gov.hk/en/gts/time/conversion.htm) 对应日期，记录公历结果及实际来源；仍有闰月歧义时保留候选，取得确认后再排。无法取得独立历表时如实记未独立核历，不把同库往返说成外部验证。八字脚本不直接接受农历字符串。
- **海外当地时间、历史夏令时**：先读 [特殊时制核验](time-normalization.md)，用 `time_normalize.py` 依IANA地区时区换算同一真实时刻，保留原始钟表、偏移、夏令时和数据版本。重复时刻保留候选，跳时造成的不存在时刻先查原记录。只有明确采用固定UTC+8排盘口径后，才将归一化结果接入 `bazi.py`；不能给海外钟表值直接贴上 `+08:00`，也不能声称换算时区已经验证了出生记录。
- **真太阳时或地方平太阳时**：特殊时制模块可作经度与太阳钟面的敏感性校核，具体精度及支持范围见 [计算约定](time-normalization.md)；这些钟面结果不是现有八字脚本的可用输入。单改生日时刻而不一致地处理节气比较，可能错排年、月柱；完整太阳时排盘仍需明确方案和独立核盘。库 [FAQ](https://6tail.cn/calendar/faq.html) 也说明不直接支持真太阳时。
- **时辰不详**：留空并说明时柱无法确定，保留有依据的候选时段；不填 12:00、00:00 或按经历“反推准确时辰”。本脚本完整四柱模式会拒绝缺失时刻。只知道“子时”等范围时，应澄清跨日及具体范围，并重排候选；不能把范围中点写成出生事实。若客户撤回先前时刻，除了时柱，还须重新评估取格所用透干、救应、起运日期与交运年份；不能仅删除时柱而保留原来整套运年结论。明确标注的假设边界试算仅用于敏感性检查，不当成新确认的生日。

保守输入范围为公历 1901—2100 年，与天文台对照表范围对齐；不是对整个区间每一天的外部验证承诺。出生资料原为当时民用时制的，还须单独校核，固定 UTC+8 不替代历史时区资料。

## 日期核验：先确认是哪一天

`calendar_input.py` 与八字共用固定依赖，只处理明确采用UTC+8标准时口径的公农历日期。它不生成出生时刻、不计算八字，始终输出 `date_only=true`、`bazi_ready=false`。输入范围按最后公历日期1901-01-01至2100-12-31检查；农历1900年末有一部分落在此范围内。

```bash
.venv/bin/python scripts/calendar_input.py lunar \
  --year 2023 --month 2 --day 1 --leap yes --time-basis utc8-standard
.venv/bin/python scripts/calendar_input.py solar \
  --date 2025-01-29 --time-basis utc8-standard
```

两例分别为2023闰二月初一→2023-03-22、2025-01-29→2025正月初一。农历输入必须显式 `--leap yes/no`，不把不清楚闰月当成“不是闰月”。月参数保持1—12正数，库所用负月号由助手内部处理。先核该年是否有该月，再核该月是29天还是30天，最后转换并回读；不存在的闰月与日期直接拒绝。例如2024年腊月只有29天，不能以“腊月三十”进入排盘。

用户同时给了公历和农历时，把公历传入 `--expected-solar YYYY-MM-DD`，不一致即返回错误，先查原始记录。这个比对只证明两项输入是否符合所用库，不证明哪份生日记录才是真实的。

结果里的 `solar_date` 是换算后的日期，`lunar_date` 保留闰月与实际月天数。`lunar_year_label` 以正月初一换年，可用于采用农历年界的梅花时间法；它不是以立春换年的八字年柱。可选 `--hour-branch` 只原样记录用户明确给出的时支及序数，不会推算几点几分，也不解决子时跨日。

接入八字时，再取得实际出生时刻、时制及误差，构造独立的完整输入；不能把日期API内部使用的00:00当成用户生日。只有日期、没有时间时，完成日期核对并指出还缺时刻，不伪造完整盘。公历日期转换本身不要求出生时刻。

接入梅花或小六壬时，先按该方法选定的日界确定日期，再将核过的农历年月日与真实时支传入；参数不会自动跨日。农历存在某个闰月不等于已经决定该术法如何取数，梅花与小六壬的闰月方法仍按各分支规则。海外当地日期、真太阳时和历史夏令时不通过此工具自动归一化。

该助手的往返检查属于同库内部一致性。香港天文台样例是有限的外部抽查，不能据此声称1901—2100每一天已经逐项校准。命令出错时不会输出成功的半份日期结果，下游不得继续排盘。

## 运行

优先复用 skill 目录内已经就绪的 `.venv`。首次使用而环境尚未就绪时，在该目录创建隔离环境并安装固定依赖，再运行。命令中的日期是明确的测试输入，示范用途不授权给缺时辰用户补时刻。下方多行示例使用 macOS/Linux shell；Windows PowerShell 请使用对应的单行命令，不能直接照抄反斜杠续行。

```bash
python3 -m venv .venv
.venv/bin/python -m pip install -r requirements.txt
.venv/bin/python scripts/bazi.py \
  --solar '2005-12-23T08:37:00+08:00' \
  --time-basis utc8-standard \
  --day-boundary 00 \
  --uncertainty-minutes 5 \
  --details
```

Windows PowerShell（同样在 skill 目录内运行，无需激活环境或修改执行策略）：

```powershell
py -3 -m venv .venv
.venv/Scripts/python.exe -m pip install -r requirements.txt
.venv/Scripts/python.exe scripts/bazi.py --solar '2005-12-23T08:37:00+08:00' --time-basis utc8-standard --day-boundary 00 --uncertainty-minutes 0 --details
.venv/Scripts/python.exe -m unittest discover -s tests -v
```

最低 Python 3.9，本次在 Windows / Python 3.12 复测。依赖固定为 `lunar-python==1.4.8` 和 `tzdata==2026.4`；脚本核对历法库实际版本，缺包或版本不符即停止，不以心算代替。时区工具优先使用系统 IANA 数据，缺失时使用 `tzdata`，并在结果中记录实际来源和版本；依赖锁定不代表所有平台的系统时区数据相同。安装依赖需要网络，排盘本身不联网，也不向外发送出生资料。命令行标准输出与标准错误使用 UTF-8；通过 Python 子进程调用时指定 `encoding="utf-8"`。`--details` 可选；其藏干次序与十神表使用库约定，未给藏干赋权。大运为可选模式，须同时传入 `--gender male/female` 与 `--yun-sect 1/2`；只传其一报错。它们表示本次采用的传统排运参数，不从姓名、称呼或性别表达推断。没提供时只给四柱，不编起运年龄。

`--uncertainty-minutes` 表示用户资料估计误差的正负分钟数，须在 0—1440 内；未知可省略。省略会明确标记未评估，不等于误差为零。`0` 只用于已经确认采用输入瞬间的计算，不证明记录绝对无误。仅给时分时，程序采用秒数 00 作为可复现约定并标记秒数未知。

## 方法口径

本版以 [6tail 原项目](https://github.com/6tail/lunar-python) 的 `Solar.fromYmdHms(...).getLunar().getEightChar()` 为底座，不自行实现天文历法。API 与原代码核查日期：2026-09-14。

按 [EightChar 官方 API](https://6tail.cn/calendar/lunar.bazi.html)，年柱以立春交接瞬间分界，月柱以十二“节”分界。农历日期由民用公历日期转换，和八字换日规则分开输出。春节日期与立春日期不同，不能用生肖年直接替代年柱。[香港天文台节气说明](https://www.hko.gov.hk/en/gts/time/24solarterms.htm) 解释二十四节气与太阳黄经关系；其 [节气数据说明](https://www.hko.gov.hk/sc/gts/astronomy/Solar_Term.htm) 明确时间为香港时间，即 UTC+8。

日柱换日必须显式选定，程序同时输出另一口径供核对：

| 参数 | 对应 API | 23:00—23:59 的日柱 | 同时段的时柱 |
|---|---|---|---|
| `--day-boundary 23` | `setSect(1)` | 按翌日 | 按翌日日干起时 |
| `--day-boundary 00` | `setSect(2)` | 按当天 | 仍按翌日日干起时 |

这两个选项不是所有子时流派的全集。特别是 `00` 并不表示“晚子时时柱也用当天日干”。晚子时有差异时保留双盘；十神分别以各自日主重算。不得将一派日柱和另一派十神混合成一个命盘。

## 大运与流年参数、计算口径

```bash
.venv/bin/python scripts/bazi.py \
  --solar '2022-03-09T20:51:00+08:00' \
  --time-basis utc8-standard --day-boundary 00 \
  --gender male --yun-sect 2 --dayun-count 8 --liunian \
  --uncertainty-minutes 0 --details
```

日期与误差0仍只为测试复现。`--dayun-count` 为1—12步，默认8，**不包括起运前区段**；`--liunian` 可选，附每步10个流年干支标签。提供这两项的自选值须有完整排运参数。`--day-boundary` 与 `--yun-sect` 是不同的流派开关，不能互相代替。

本版直接检查已安装1.4.8的 `EightChar.getYun`、`Yun`、`DaYun`、`LiuNian` 及 `Solar.subtractMinute/nextYear/nextMonth` 实现，接口对照[原项目 Yun](https://github.com/6tail/lunar-python/blob/master/lunar_python/eightchar/Yun.py)。网上 `master` 会变化，运行仍固定1.4.8。

| 项目 | 明确采用的规则 | 输出如何复核 |
|---|---|---|
| 顺逆 | 立春年干：甲丙戊庚壬为阳，乙丁己辛癸为阴；阳男阴女顺，阴男阳女逆 | `direction_basis` 留年柱、年干、阴阳、gender的API值与方向 |
| 取节 | 顺行从出生至严格晚于出生的下一“节”；逆行取不晚于出生的上一“节”。恰好同秒时，逆行取当前节，顺行取再下一节；不取最近的任意节气 | `target_jie` 列节名、时间及与出生秒差；逆行可为0 |
| 起运算法1 | 日差与时辰序差折算；三天一年、一天四月、一个时辰十天。库将23时的折算序号专设为11 | `start_offset` 的年月日；小时为0。它不是按秒比例折算，勿将小时分界与日柱流派混用 |
| 起运算法2 | 两端各去秒后求分钟差；4320分钟→1年，360分钟→1月，12分钟→1日，余1分钟→2小时 | `start_offset` 的年月日时。出生秒数虽会保留在最终日期中，并未参与此折算 |
| 起运公历 | 依次加所得年、月、日、小时；年/月加法由库截到有效月末 | `start_solar`，注明是库算法值，不是独立历书已核准的真值 |
| 大运干支 | 从出生月柱沿六十甲子顺或逆走，每步一位 | 第1步不是月柱本身；`pre_start_phase` 单列，干支为空，不伪作十年运 |
| 年龄与年份 | 起运公历年起，每行十年标签；年龄标签=该公历年−出生公历年+1 | 字段明名 `start_year_label`、`start_nominal_age`；不是周岁，也不是按农历春节逐日计算的虚岁 |
| 流年 | 列相应公历年份立春起的干支年名称 | `liunian` 不意味着元旦换流年；在交运年份仍需区分交运前后 |

《三命通会》卷二[《论大运》](https://zh.wikisource.org/wiki/三命通會_(四庫全書本)/卷02#論大運)可核顺逆与三日一年的传统来源；古文另涉及月日折除等说法，不据这条书目就宣称现代库的两种公历加法均为古法唯一真传。

交节等号归属是固定库 `Lunar.__getNearJieQi` 的实现契约，不冒称各派通则。例如库算2024-03-05T10:22:45+08:00交惊蛰，阳年男顺行在前一秒取惊蛰，到该秒改取清明；女逆行到该秒取惊蛰，起运偏移为0。算法2在同一分钟内还可能因忽略秒数算得0偏移。此例只锁定程序行为，不证明交节秒数经外部核验；真实出生记录碰到该边界时必须分别重排候选，不把跳变掩盖成精确起运。

**表格最易误读处**：例如算法2的测试结果为2030-12-12起运，而首行会标2030—2039。2030年大部分时间仍未起运，不能把整年归入首运。本脚本没有输出后续每一运的精确交接时刻，也未自动生成出生误差上下限所造成的起运范围。所问问题依赖这些细节时，分别重算候选并取得同口径外部排运设置。

上述示例的复核值：年干壬、阳男顺行，取下一节清明2022-04-05；算法2起运偏移8年9月2日10小时，起运公历2030-12-12T06:51:00+08:00，前两步甲辰、乙巳；改算法1时起运日期为2030-12-19。日期差异是算法约定差异，不能挑更合经历的一项假装校准精度。

## 边界与停止条件

JSON 包含计算引擎版本、输入、口径、四柱、另一换日口径、民用农历日期、邻近节气和警示。`verification` 始终说明本次没有自动独立核盘。`computed` 仅表示已计算，不等于实证预测准确，也不代表出生记录已核实。

`boundary_review` 的操作窗口为 `max(5 分钟, 已提供的出生误差)`；5 分钟是人工核查缓冲，不是库的误差保证或统计置信区间。事件 `affects` 标记可能变化的柱：立春涉及年、月；其余节涉及月；中气不直接改变月柱；奇数整点涉及时；选定换日点涉及日。出生误差未知时，无边界警告也不能证明时柱可靠。

窗口触及影响解读的边界时，先核实原始记录并查权威节气时刻，再把边界两侧分别重排为候选盘。邻近节气显示到秒只为复现库结果，不能声称秒数已外部验证。天文台对照表也提示远期天文计算存在分钟级不确定性，接近午夜时可能影响日期。

非零退出码、错误 JSON、来源日期冲突或外部盘不一致时，停止命理结论，先排查历别、闰月、时区、夏令时、立春节令和换日流派。输入条件不能澄清时，交付候选与缺项，不挑“看上去更准”的一盘。

## 已做验证与证据边界

运行 `python -m unittest discover -s tests -p 'test_bazi.py' -v`。测试分三层，互不替代：

1. **外部历法抽查**：天文台 [2024 对照表](https://www.hko.gov.hk/en/gts/time/calendar/text/files/T2024e.txt) 的 2024-02-10＝正月初一；[2023 中文对照表](https://www.hko.gov.hk/tc/gts/time/calendar/text/files/T2023c.txt) 的 2023-03-22＝闰二月初一。两项与库输出一致，只验证这些日期转换。测试使用 12:00 是人为固定测试时刻，不是对用户缺时辰的填补规则。
2. **外部节气分钟抽查**：天文台 [2024 年历](https://www.hko.gov.hk/tc/gts/astron2024/files/HKO_almanac_2024.pdf) 二月表记载 2 月 4 日 16:27 立春；库返回 16:27:07，与公开资料分钟精度相合。外部资料未证实此 07 秒为真值。两侧一秒切换测试检验代码遵循库边界，不是秒级天文精度证明。
3. **上游样例回归与失败边界**：[原项目 EightCharTest.py](https://github.com/6tail/lunar-python/blob/master/test/EightCharTest.py) 的 `test_gan_zhi`、`test7`、`test10` 对应普通、凌晨及晚子时四柱。本版另测换日、立春、中气、误差窗口、非法输入、缺包与版本不符。上游自测仅证明调用兼容，不构成独立命理验证。

新增大运回归对照[原项目 YunTest.py](https://github.com/6tail/lunar-python/blob/master/test/YunTest.py)的 `test`、`test3`、`test4`、`test5`、`test6`；另检查四组顺逆、立春前后方向、起运算法与换日互相独立、分钟折算忽略秒、月柱顺逆递推、流年标签、起运前区段与非法参数。该组证明固定库调用及约定得到遵循，不构成外部排运验证。
